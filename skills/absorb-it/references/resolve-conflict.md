# Playbook — resolve-conflict  (finish a conflicted merge or rebase, with the intent evidence)

Recipe: Matt `resolving-merge-conflicts` (removed upstream in v1.3.0, no successor; kept here).
A conflict is two intents meeting, not a text problem.
The conductor's union rebase (merge-serialization.md), a lockfile chain, and a fix round after the
upstream moved all land here. The output is a finished merge AND the record a re-reviewer needs,
because a resolution that changes content voids the review that preceded it.

## 1. See the actual state first

Which operation is in progress (merge, rebase, cherry-pick), which commit is being applied, which
files conflict, and which hunks inside them. Read it from git, not from the last worker's summary —
a resumed session's memory of the conflict is not the conflict.

## 2. Find the primary source for EACH hunk

For every conflicting hunk, both sides have an intent. Recover it from the sources that own it: the
commit message, the PR that carried it, the issue or finding it closes, and the intent packet on
its evidence manifest (evidence-manifest.md) — open-fleet's builders record `goal` · `ruled_out` ·
`why` precisely so this step is not archaeology. A hunk whose intent cannot be recovered from any
of these is escalated, not guessed.

## 3. Resolve

- **Preserve BOTH intents** wherever they can coexist.
- Where they cannot, keep the one matching the STATED GOAL of the merge in progress, and record the
  trade-off with the intent that was dropped and why.
- **Never invent behaviour.** A resolution that is neither side — a "cleaner" third version, a
  rename, a tidy-up, a helper extracted while you were in there — is a code change smuggled through
  a merge, invisible to the review that approved either side. If the correct result genuinely is
  neither side, STOP and route it as a change unit (read build-change.md).
- **Always resolve; never abort.** `--abort` throws away the analysis and hands the same conflict
  to the next attempt. If the resolution cannot be made, stop WITH the conflict in place and
  escalate through the gate (gate-classification.md) — a stopped, documented conflict is
  resumable; an aborted one is not.
- Generated artifacts (lockfiles, snapshots, build outputs) are never hand-merged: take the
  resolution from the generator, re-run it, and cite the command.

## 4. Run the project's own checks

Discover the checks the project actually runs — typecheck, tests, formatter, linter — and run them,
in that order. Fix what the merge broke, and only that: a failure that predates the merge is a
finding, not this unit's work. Paste the commands and their exit codes.

## 5. Finish and hand back

Stage everything and complete the operation; for a rebase, continue until every commit is applied.
Then emit the resolution record:

```
CONFLICT RESOLUTION
base=<sha> onto=<sha> op=<merge|rebase>
per hunk: <path>:<range> — kept=<side|both> intent-a=<…> intent-b=<…> trade-off=<…|none>
generated: <path> — regenerated by <command>
checks: <command> → <exit> (×N)
content-changed=<yes|no>
```

## Review consequences (fail closed)

If `content-changed=yes` — any hunk where the resolved text differs from both parents, or where one
side's intent was dropped — the resolution VOIDS the prior review per reviewed-sha-freshness.md.
The unit re-enters build-blind review (`acceptance-review`) at the new head, and the re-reviewer is
handed the resolution record as its input, not the diff alone. A resolution that is a pure content-
identical replay of one side keeps the review, and the record says so explicitly. When in doubt,
`content-changed=yes`: re-reviewing a clean rebase is cheap, merging an unreviewed change is not.

## Completion

The operation is finished (no conflict markers anywhere in the tree, no in-progress state); every
hunk has both intents recorded and a kept-side with a reason; no behaviour exists in the result
that existed on neither side; generated files were regenerated by their generator with the command
cited; the project's checks ran with pasted exit codes; `content-changed` is recorded, and where it
is yes, the unit is back in review at the new SHA before it can merge.
